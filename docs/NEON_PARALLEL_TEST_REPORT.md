## خط الأساس والاختلاف عن Supabase

أُنشئت واجهات SQL اختبارية لـ`auth.users` و`auth.sessions` و`auth.uid()` و`auth.jwt()` وبيانات Storage والأدوار `anon` و`authenticated` و`authenticator` و`service_role`. هذه ليست خادم Supabase Auth أو Storage. أدوار المستخدمين الاختبارية NOLOGIN ودون BYPASSRLS؛ مالك قاعدة Neon هو منفذ الترحيلات والدوال ذات SECURITY DEFINER.

نُقلت ملفات خط الأساس الـ49 إلى قاعدة الاختبار. ظهر رفض حقيقي لإعداد PostgREST:

`alter role authenticator set pgrst.db_schemas = 'public,graphql_public'`

هذه العبارة من `20261013230449_configure_public_data_api.sql` خاصة بإعداد خادم PostgREST. لا يوجد ذلك الخادم في اختبار Neon هذا. أُضيف استثناء واحد مطابق حرفياً في محول الاختبار، وسُجل في `provider_omissions`؛ لم يتغير الملف الأصلي، ولم يُخف فشل أو يُتجاوز أي SQL تطبيقي. سُجلت SHA-256 للملفات الأصلية. تحفظ التجربة سجلاً منفصلاً اسمه `maystroon_test_harness.migration_runs`، وليس سجل إنتاج Supabase.

رفض النقل الأول إرسال عدة أوامر داخل prepared statement. أُضيف splitter يحافظ على نص العبارات وأجسام الدوال والتعليقات والاقتباسات، ثم نُفذت العبارات في transactions. فشل محاولة خط الأساس الأولى عند إعداد PostgREST ألغى كامل دفعتها؛ نُفذت الدفعة لاحقاً مع الاستثناء الموثق فقط. لم يُجر أي إصلاح يدوي لسجل إنتاج.

- `scripts/neon-test-harness.mjs`: هدف Neon صريح وثابت، تقسيم SQL، payloads الترحيلات وsuite القبول، وchecksum لكل ملف. لا يقرأ أسرار الإنتاج أو يعيد توجيه التطبيق.
- `scripts/sql/neon-test-bootstrap.sql`: واجهات SQL الاختبارية فقط؛ لقاعدة جديدة، لا يعاد تشغيله على القاعدة المكتملة.
- `scripts/sql/neon-capture-baseline.sql`: يُشغّل بعد الـ49 وقبل الستة؛ يحفظ بصمات الأصل وfixture الاحتفاظ.

لإعادة التجربة استخدم فرعاً وقاعدة اختبار جديدين وحدد الهدف الصريح قبل أي تشغيل. استعمل Neon transaction API لكل payload ناتج عن migrationBatch؛ اتصال HTTP لا يقبل ملفات SQL كاملة متعددة الأوامر في prepared statement واحدة. لا تعِد تطبيق ملفات السجل على القاعدة المكتملة، ولا تستخدم reset أو حذف قاعدة قديمة كإجراء إصلاح. لا تُسجل connection strings ولا تضفها إلى git.
