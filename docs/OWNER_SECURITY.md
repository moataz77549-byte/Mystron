# Owner security

Production owner email: mtzallqmy@gmail.com. Email equality does not grant a role. Create/verify a real Supabase Auth identity, independently verify its UUID, then a trusted database operator invokes the existing one-time private.bootstrap_owner(UUID). The bootstrap row is locked and permanently closed on success. No default account or PIN is installed. Until then the login page reports Pending Setup. No routine application endpoint transfers ownership or creates another OWNER.

PIN is additional protection, 6–12 decimal digits. Existing salted scrypt-v1 is retained: N=32768/r=8/p=1, 64-byte output, random 16-byte salt, HMAC-SHA256 with a separate server PIN_PEPPER of at least 32 characters. This is a memory-hard KDF with a server-held pepper; there is no plaintext PIN storage. PIN_PEPPER loss/rotation requires secure PIN reset after reauthentication.

`/auth/pin` requires a live confirmed OWNER session, exact Origin, shared rate limiting and database backoff. Failed verification delays grow exponentially to 15 minutes. Save/reset requires fresh password reauthentication of the same Auth UUID; if MFA is enrolled, the existing session must have aal2. Sensitive permission/security changes require both a recent PIN proof and fresh password reauthentication. The separate reauthentication session is not retained.

Proofs use 32 cryptographically random bytes in an HttpOnly, Secure on HTTPS, SameSite=Strict cookie. Only SHA-256 of the nonce is sent in the server-to-PostgREST header/stored in private.sensitive_proofs. Proofs bind owner UUID, actual Auth session UUID, current PIN epoch, 1–15 minute expiry; strong assurance lasts at most 5 minutes. Changing PIN increments the epoch and invalidates previous proofs. PIN and tokens are never returned to UI, written to audit metadata or security event fields. Only fixed operation-stage/error-class diagnostics are logged for unexpected PIN failures.

Optional PIN enforcement applies to user/invitation/settings/menu/advertisement/integration/maintenance administration. Roles and security remain protected even when optional enforcement is disabled. Higher-risk ownership/recovery changes have no ordinary UI mutation and require an independently reviewed strong-auth procedure. Do not bypass MFA or bootstrap during activation.

Invitations: random 256-bit tokens, only hashes in the database, 1–168 hour UI expiry, verified matching email, actor-authority recheck on acceptance, row lock and single-use status. Supabase Auth delivers the invitation/magic link. `/invite` removes token/fragments from browser history immediately; the server validates the Auth session before the database can accept it. Referrer-Policy, no-store and noindex reduce incidental link disclosure. Configure allowed redirect URLs and SMTP before production use; no test mail was sent to real people.

/admin/security can revoke an individual other administrative session after strong PIN reauthentication. It writes a durable revoked Auth session ID; subsequent administrative RLS/RPC/API checks fail immediately, including token refresh using the same session ID. It does not delete Auth metadata or claim revocation from unrelated services. The current session uses the normal logout flow.
