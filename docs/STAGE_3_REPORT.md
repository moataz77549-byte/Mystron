## Supabase: المطبق فعلياً والعائق

المشروع المستخدم حصراً: **ttvasynaxkkcwrmvlorg**، مشروع فذكر السابق الذي أذن المالك بإعادة استخدامه. القراءة الأخيرة: 6 أقسام، 8 أدوار، 25 صلاحية، صفر تدوينات، صفر مستخدمي Auth، وصفر جداول تطبيق دون RLS. ما زالت مهمتا النشر والاحتفاظ من المرحلة الثانية مفعّلتين.

أُضيفت في المصدر 19 migration للمرحلة الثالثة. نجح تطبيق اثنتين فقط:

1. 20261015213017_control_01_admin_schema.sql
2. 20261015213134_control_02_admin_default_grants.sql

**الـ17 التالية غير مطبقة إنتاجياً.** أعاد الاتصال `McpServerError: Invalid or expired requestState` عند ترحيل التفويض، حتى بعد تقسيم الطلب إلى أجزاء أصغر والتحقق أن العملية لم تُطبق. لم يُسجل هذا كنجاح، ولم يُتجاوز الخطأ بتعديل سجل migrations أو تشغيل DDL عبر مسار بديل غير مراجع. راجع ملفات migrations المرتبة؛ أول ملف معلق هو control_03_admin_authorization.

أُنشئت بنية permissions/role_permissions/user_permissions/admin_memberships/admin_invitations/security_events/admin_notifications/menu_items/integration_settings وprivate.pin_controls/sensitive_proofs؛ ويكتمل revoked_admin_sessions والدوال والسياسات عبر الترحيلات المتبقية. أُغلقت صلاحيات الجداول الجديدة افتراضياً مع RLS فور إنشائها. دالة admin_identity لم تكن موجودة في التحقق الحي الأخير، لذلك إدارة المرحلة الثالثة تفشل مغلقة إلى حين إكمال الترحيلات.

تمت مطابقة اسمي وتوقيتي الترحيلين المطبقين مع سجل الخادم، وترتيب ملفات البقية بعدهما دون تكرار الجداول أو تغيير تاريخ ترحيل مطبق.

فحص Supabase الأمني في هذه الحالة الجزئية: 15 ملاحظة INFO عن جداول RLS بلا سياسات، بعضها خاص مغلق عمداً وبعضها ينتظر بقية المرحلة؛ و12 WARN لدوال SECURITY DEFINER من CMS السابق ذات تفويض صريح. ليس هذا تقرير خلو كامل من الملاحظات. مراجع المراجعة:

## الأمان الذي عولج

استُبدلت حراسة أسماء الأدوار وحدها بتفويض فعلي في قاعدة البيانات. لا تكفي صلاحية تعديل المقال لتغيير حالة مقال منشور؛ يلزم النشر أيضاً. لا تتجاوز الدعوة أو تغيير الدور رتبة/صلاحيات/أقسام من ينفذ العملية. سحب الوصول يراجع session_id فعلياً؛ ولا يعاد تنشيط الجلسة المبطلة بتحديث JWT. إثبات PIN مرتبط بالجلسة والمدة والحقبة، وتغييره يلغي السابق. لا تظهر hashes أو tokens أو بريد التعليقات في API العام. الروابط والقيم والإعدادات محددة البنية، وHTML المقال معالج، والسجلات لا تتضمن كلمات مرور أو PIN.

## غير مكتمل والإجراءات المطلوبة

1. إكمال اتصال Supabase الذي يسمح بتطبيق ترحيلات الوظائف الأمنية، أو تشغيل الترحيلات المرتبة عبر CLI بحساب المالك الموثوق. السبب الحالي خطأ حالة طلب الاتصال، وليس فشل SQL مثبتاً في الاختبارات المحلية.
2. إنشاء هوية المالك الحقيقية وتأكيد بريدها والتحقق المستقل من UUID، ثم bootstrap موثوق لمرة واحدة. حالته الآن Pending Setup؛ لا يوجد مالك إنتاجي أو PIN معين.
3. إعداد مفاتيح الخادم في الاستضافة: SUPABASE_SERVICE_ROLE_KEY وRATE_LIMIT_SECRET وPIN_PEPPER وCRON_SECRET، وإعداد Auth redirect URLs وSMTP. لا تُرسل الأسرار أو كلمات المرور أو OTP إلى المحادثة أو GitHub.
4. ربط Vercel بالمستودع الرسمي وإعداد البيئة ثم إنشاء Preview والتحقق من عنوانه على الهاتف والكمبيوتر. لم يُنشأ رابط نشر ولم تُنشر نسخة إنتاجية.
5. إجراء قبول حي للمصادقة والدعوات وMFA إن فُعّل وStorage والسياسات بعد إكمال الترحيلات؛ إعادة فحص advisors وتوليد أنواع قاعدة البيانات من الحالة النهائية.
6. استكمال دخول لوحة Supabase لمراجعة أسرار/إصدارات Edge القديمة وتغيير الاسم المعروض؛ ما زالت تسعة سجلات Edge قديمة بأجسام 410 خاملة، ولم يُدّع حذفها النهائي.
7. تفعيل سياسة نسخ حقيقية واختبار استعادة منفصل عند توفر الموارد؛ لا توجد حالياً نسخة أو تجربة استعادة ناجحة موثقة.

لا توجد تحليلات مصادر زيارات/أجهزة مخترعة. التكامل الفعلي مع Telegram وBotKeep وAI مؤجل للمرحلة الرابعة. **المشروع غير جاهز لاعتماد المرحلة الثالثة إنتاجياً أو الانتقال إلى الرابعة قبل حل العوائق المذكورة والمراجعة.**
